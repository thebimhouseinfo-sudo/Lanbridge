## Baseline and decisions to validate

- `internal/mcpfwd/fwd.go` currently has one stdio session per project and ignores server notifications. `cmd/bridge/main.go` obtains one project session and checks the project/grant; `internal/projectconfig/store.go` has transport, command and URL fields. Windows profile setup currently defaults to stdio, and changing an existing endpoint is not a complete UI flow.
- `internal/fileops/sync.go` uses a grant, resolved paths, a 5 MB cap, protected config checks and atomic rename, but no version precondition. `permissions.Resolve` resolves existing symlink ancestors. Existing project readiness covers read/sync/exec/MCP. The new maintenance route must be separate and must not make other project operations ready.
- Mac agent gateway and Bridge host currently share project-level MCP state. They do not prove isolation of distinct conversations; do not present a project-wide shared session as conversation isolation. Verify which stable identity the Mac host actually supplies before implementation; if it does not supply one, report isolation unsupported and fail closed for a server requiring it, rather than inventing identities.
- Source root on this Windows host is `D:\00 Other Works\Vibecode\Testbridge`; it is a verified current checkout, not a portable default for other installs. Provision that verified root during upgrade/setup so paired Read/Sync works by default without project configuration, display it and make the entitlement revocable. If no source root can be established reliably on a different installation, expose a clear local selection rather than scanning arbitrary drives. Verify upgrade preserves the root and that the existing live Bridge can receive it when project configs fail.

## M11 — Generic MCP transport, configuration and session

**User outcome.** Windows configures or changes one project's MCP connection without losing grants; test reports reachability and a sanitized diagnosis. The Mac agent discovers and invokes tools through Bridge after existing project readiness, grant and blacklist checks. Local Windows endpoint defaults to loopback. No secret enters normal UI state, errors, logs or Mac messages.

**Implementation boundaries.** Extend the project config/UI operations in `internal/projectconfig`, `internal/ui` and `cmd/bridge` to validate and atomically update only MCP connection fields in the existing profile; preserve unknown/unrelated permissions and the currently loaded project. A connection test initializes and discovers only; it does not call a project tool or change grants/profile. Offer stdio command/arguments or an HTTP endpoint and an optional local secret reference. Persist secrets separately in user-local OS-protected storage, never in the transferable project data; a UI only indicates that a secret is set, and permits replacement/removal. Validate URL and reject credentials/query secrets in user-facing representations; do not echo underlying library error URLs. Verify platform secret-store capability and installed deployment dependencies before selecting the smallest mechanism; a missing store produces a clear blocked status rather than plaintext fallback. This proposal does not require an external service.

Treat the complete endpoint URL as potentially secret, including path and query: Windows accepts it once, stores the entire value in its local protected secret store, and shows only an opaque label/set-or-unset status thereafter. Supply the value only to the local HTTP client; never send it to Mac or UI snapshots. Redact endpoint paths, queries, headers and transport errors across request, SSE, reconnect, logs and diagnostics; disallow redirects unless revalidated and ensure no credentials are forwarded across origins. Audit existing `agentmcp` notification error logging as well. Test path-token, query-token and header-token leakage, including redirect and failed-connection paths.

Project changes use a per-profile locked, atomic read-modify-write that preserves unknown JSON fields as well as grants. Validate first; write a temp file and replace atomically; only then update the in-memory project and close the old session. On write failure keep both old disk and runtime state, with a sanitized error. Test refresh and rollback, including unknown fields. Do not rely on the current `SaveWindows` struct round-trip, which drops unknown fields.

Extend `internal/mcpfwd` behind a common session interface for stdio and MCP Streamable HTTP, reusing existing session/manager ownership instead of a separate proxy service. HTTP uses the MCP server's initialize/initialized handshake, negotiated protocol and session ID, correctly parses JSON and SSE responses, handles server event streams and disconnects, and closes resources. Keep tokens local to Windows. A per-call timeout bounds stalled calls; no automatic replay of a potentially mutating call after a timeout or disconnect. Reconnect on the next explicit call or discovery only, then refresh tools. Process `notifications/tools/list_changed` for both transports, refresh the tool cache asynchronously, and emit Bridge's existing notification. Preserve tool schema and metadata needed by the client; no truncation beyond explicit supported client limits.

**Isolation and callbacks.** First perform a bounded real-client spike with Codex and Claude: identify what distinct client/process/session scope is actually supplied and demonstrate two independently initialized sessions against a generic server and CadGPT outer admission. Choose a compatible boundary with evidence; do not copy CadGPT ChatGPT identity or reuse a session across independent conversations. If required scope cannot be represented, document and address the integration gap before claiming the requested CadGPT capability; a generic fixture alone is insufficient. Dispose sessions on disconnect, config replacement/revoke and Exit; do not reuse a session after changing transport, endpoint or credentials. Concurrent lists/calls and stale notifications must not revive a closed session. Apply blacklist before forwarding, and never treat a missing blacklist as empty.

Candidate scope path: generate a unique opaque ID for each actual `bridge mcp` client process, send it on every forwarded request through the authenticated paired connection, and key host sessions by connection + client ID + project. Retire all scopes on client disconnect/Exit and reject stale IDs. Never synthesize `x-openai-subject` or `x-openai-session`. **Blocking spike:** verify whether Codex/Claude isolate chats by MCP process or supply a genuine finer scope. If multiple chats share one MCP process without a real scope, this candidate does not satisfy chat isolation; M11 stays BLOCKED until a host-supported isolation mechanism is demonstrated. Do not infer a server's identity requirements or claim generic server isolation merely because an initialize call succeeds.

**Verification.** Generic stdio plus HTTP fixture exercise initialize, negotiation, session header, JSON/SSE, notifications, pagination, config update preserving grants, missing config, access denial, timeout, malformed responses, server restart and no replay, concurrency, isolation and secret redaction. Test at least one independently implemented generic MCP server, not only in-tree fixtures. Test CadGPT outer MCP on two machines with explicit test drawing only; if host identity is not available, record BLOCKED with no bypass. Test supported blacklist matching and show why OPEN/LISP/Shell cannot be universally blocked by textual tool matching.

## M12 — Narrow Bridge source maintenance

**User outcome.** A paired Mac reads and syncs the Windows Bridge source even when project config is unavailable. Windows UI shows the exact source folder and the default Read/Sync setting; user can revoke and re-enable it. No automatic Exec, MCP grant or access to any other project. No Windows coding agent is needed.

Mac is the development side: changes originate on Mac and are sent to Windows for build/test. The Mac agent can query the allowed Windows source root, available project/transport configuration status and other non-secret metadata needed to configure an existing server, subject to the existing grants; it must never receive tokens, private config contents or ungranted folder listings. It can inspect files within already-granted folders and use existing allowed build/exec operations. Routine sync does not generate user-facing change notices, prompts or repeated permission requests; actual operational errors remain visible to the agent. MCP `tools/list_changed` is a protocol event for discovery, not a user change notification, and remains required.

**Implementation boundaries.** Introduce a locally persisted, explicitly identified source root and enabled flag, owned by the existing Windows host state/UI; initialize only from the locally selected known source. Add narrowly named maintenance Read/Sync operations to the existing authenticated paired transport and Mac `agentmcp` tools. They bypass only project-ready and project folder grants, not pairing or maintenance entitlement; route ordinary project calls through existing guards. Reuse `permissions.Resolve` and `fileops` limits and write mechanics, with a separate maintenance authorization argument rather than installing a synthetic grant in the project's mutable grant list. Every list/read and sync checks current entitlement so revoke affects the next operation. Do not send private paths or file contents in errors.

Provision the verified current source root through the Windows upgrade/setup package or an existing locally stored installation setting; no hardcoded machine path in product source. Persist the entitlement per paired device, default enabled for the verified root; UI shows the root and permits revocation. Missing, moved or unverifiable root is reported unavailable and never replaced by a guess; a local user can select a replacement. Test initial connection without project config, reinstall, revoke and missing-root behavior. The means of provisioning that root into the installed app without relying on project readiness is a required first implementation spike.

Refuse source access to Bridge App Data/config, pairing data, credential stores, `.env`, known secret files, and Git metadata; refuse sync to these and to installed/running Bridge binaries. Resolve canonical path and existing ancestors including reparse points, check both root containment and protected paths, reject unsafe or unverifiable aliases. Name-based filters cannot discover secrets inside an otherwise allowed source file: document this limit and never call the feature a general sandbox. Do not use broad project permissions to bypass private config sync prohibition.

Reuse the existing on-demand atomic sync and locked-file handling; do not impose a new mandatory destination-hash handshake or user confirmation for normal Mac-originated changes. Return per-item results and genuine failures to the agent, with no routine user-facing notice. Respect the existing requirement not to overwrite a file actively locked by another process; detecting unsaved edits in an editor is not generally possible, so do not promise otherwise. Repeat protected-config resolution in both ordinary and maintenance sync, including aliases and junctions. Preserve project sync behavior and accurately report partial batch results. Build/test remains separately granted Exec and project readiness; if config is broken the exception supports source repair but not remote build until readiness is restored. Do not replace a running binary. Update by installing a tested package after exiting Bridge.

**Verification.** Cover paired/unpaired, profile missing, agent discovery of allowed non-secret facts, wrong root, read/sync/revoke, traversal, Windows junctions and aliases, protected locations, `.env`, config, binaries, locked targets, 5 MB limit, atomic write and no routine user notification. Regression tests prove other project grants and blacklist unchanged and Exec denied without its own grant. Physical test from Mac uses only source and approved build/test, with neither Windows agent running; report build tool prerequisites and actual results.

## M13 — Awake and idle connection

Add a small platform-specific lifecycle abstraction used by host and client process startup and Exit. On Windows use an execution-state request with correct thread lifetime; on macOS use an OS-supported idle-sleep power assertion. Keep the display free to sleep; release on normal exit and allow the OS to release on process death. Surface acquisition failure without logging secrets. No service, scheduler or persisted OS power setting. Check existing reconnect and transport deadlines: remove only inactivity-based project/session expiry if present; keep bounded individual calls, detecting true network failures and the current manual project-config reopening after reconnect. No promise against explicit sleep, lid closure, power failure or OS policy.

Wire acquisition and release to both existing `runHost` and `runClient` process lifetimes in `cmd/bridge/main.go`, including early returns and Exit. Windows implementation owns the execution-state request on an OS-thread-locked goroutine and clears it on the same thread. macOS assertion/helper remains alive until release and is terminated and waited on Exit; spike native API versus an existing system helper and verify macOS build/CGO constraints before selecting. Lifecycle tests cover normal Exit, startup errors and double release, then real-host sleep checks remain separate.

Tests use injected platform boundary for acquire/release/failure; native Windows/macOS CI verifies compilation and lifecycle where feasible. Physical machines must separately verify idle system sleep prevention, display behavior, Exit and reconnect after actual network loss.
